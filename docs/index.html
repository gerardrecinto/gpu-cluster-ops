From a number on a page to a running pod.

Each piece answers one question an on-call engineer asks about GPU serving.

Capacity planner

Weights at the chosen precision plus KV cache at fp16, 10 percent headroom, rounded to a power of two for tensor parallelism.

gpucap/plan.py

LLM serving chart

vLLM or TGI. Requests nvidia.com/gpu, tolerates the GPU taint, mounts /dev/shm, caches weights on a PVC, has a startup probe and a PDB.

helm/llm-serve

EKS GPU node group

NVIDIA AMI, a taint so only GPU pods land there, labels, and scale to zero.

terraform/main.tf

What is real, and what is not verified.

Every claim on this page comes from a command that ran. Anything that did not run is listed on the right.

Verified

  • 6 tests pass. helm lint passes and helm template renders for vLLM and TGI.
  • The planner keeps the KV cache at fp16 when weights are quantized, covered by a test.
  • Alert rules parse as YAML. terraform fmt is clean.

Not verified

  • Nothing ran on a GPU or a cluster. Image tags, vLLM and TGI flags and health paths come from their docs.
  • Alert rules were not checked with promtool or against a live DCGM exporter.
  • terraform validate did not finish: the AWS provider plugin timed out here.
  • The estimate ignores activation memory and CUDA overhead beyond 10 percent, so treat it as a lower bound.

Questions before you try it.

Why Recreate and not a rolling update?

A rolling update needs a second set of GPUs during the rollout. Recreate costs a short outage on each deploy. The runbook says when to switch.

Why a power of two?

Tensor parallelism splits attention heads evenly, so counts of 1, 2, 4 and 8 are the ones that work for most models.

Is the 70B on one H100 realistic?

With int4 weights the estimate is 52.6 GiB against 72 GiB usable, so it fits on paper. It was not run on a real GPU.
